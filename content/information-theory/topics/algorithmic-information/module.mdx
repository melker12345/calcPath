# Algorithmic Information Theory

Kolmogorov complexity and the algorithmic approach to measuring information in individual objects.

Algorithmic information theory (AIT) quantifies the information content of individual objects (strings, files, mathematical statements) rather than ensembles. The central notion is Kolmogorov complexity K(x): the length of the shortest program (in a fixed universal programming language) that outputs x and halts.

AIT provides a rigorous foundation for Occam's razor, induction, and the notion of randomness for single sequences. It is intimately connected with Shannon theory in the asymptotic regime but offers insights for finite objects that probability alone cannot.

## Kolmogorov Complexity (recap / intro)

<!-- section: kolmogorov-intro -->

:::definition[Kolmogorov complexity]{#kolmogorov-complexity}
$K(x)$ is the minimal $|p|$ such that a fixed prefix-free universal Turing machine $U$ on input $p$ outputs $x$:

$$K(x) = \min \{\, |p| : U(p) = x \,\}.$$
:::

The definition looks as though it depends on the arbitrary choice of $U$, and it does — but only barely. Because of the invariance theorem, $K(x)$ defined with respect to any two universal machines differs by at most a constant, the size of a translator program.

$K(x)$ is uncomputable, by reduction to the halting problem. We can only approximate it from above by running all short programs in dovetail fashion and taking the shortest one that has output $x$ so far.

:::intuition
K(x) is the ultimate compressed size of x: the smallest description that lets a computer reconstruct x exactly.

A random-looking string of length n usually has K(x) ≈ n; a string like 000...0 or the digits of π has much smaller K because there is a short program that generates it.
:::

:::example
Compare two length-$1\,000\,000$ strings and estimate $K$ for each.
:::

:::solution
**All zeros**, $x = 0^{1\,000\,000}$. A program that reproduces $x$ is essentially `print '0' repeated N times`, where $N = 1\,000\,000$. The fixed loop and print instruction cost $O(1)$ bits; the only part that grows is the number $N$, which needs $\lceil \log_2 N \rceil = \lceil \log_2 10^6 \rceil = 20$ bits to write down. So $K(x) \le 20 + O(1)$ — a few dozen bits, and the count barely grows even if we go to a billion zeros ($\log_2 10^9 \approx 30$ bits).
**A typical random string** $r$ of the same length. There is no pattern to exploit, so the best a program can do is carry the bits verbatim: `print` followed by the literal $1\,000\,000$-bit string. That costs $1\,000\,000$ bits for the data plus $O(1)$ for the print instruction, giving $K(r) \approx 1\,000\,000 + O(1)$.
**Sanity check.** The two answers differ by a factor of roughly $50\,000$ even though the strings have the *same length*. That is exactly the point of $K$: it measures pattern content, not length. Shannon entropy, which only sees the length and the symbol distribution, would not distinguish "structured" from "random" for a single fixed string the way $K$ does.
:::

## Algorithmic Probability and Solomonoff Induction

<!-- section: solomonoff -->

Intuition first: imagine feeding a universal machine $U$ a program produced by flipping a fair coin for each bit. A program of length $|p|$ arises with probability $2^{-|p|}$. The algorithmic probability of $x$ is then just the chance that this random program happens to output $x$ — short programs, being more likely to come up, dominate the sum. This is why the definition below weights each program by $2^{-|p|}$.

:::definition[Algorithmic probability (Solomonoff prior)]{#solomonoff-prior}
The algorithmic probability of a string $x$ is

$$m(x) = \sum_{p\,:\,U(p)=x} 2^{-|p|},$$

the total probability mass of all programs that output $x$.
:::

:::theorem[m is a universal semimeasure]{#universal-semimeasure}
$m$ dominates every computable probability distribution, up to a constant factor.
:::

That domination is the whole point: whatever computable law actually generates your data, $m$ already assigns it a non-negligible share of the prior.

Solomonoff induction uses $m$ to predict the next symbol: the predictive probability is m(x0)/m(x) for continuation 0, etc. It is the optimal predictor in the sense that its total expected squared error is bounded for any computable environment.

:::intuition
Instead of assuming a particular probability model, consider every possible program that could have generated the data you have seen, weighted by 2^{-length of program}. Simpler (shorter) programs that fit the data get higher prior weight.

Future predictions are the weighted average over all consistent programs. This automatically embodies Occam's razor in a formal, prior-free way.
:::

:::example
Predict the next coin toss after seeing $n$ heads in a row, using a tiny two-program toy model of the universal mixture. This is a caricature (the real mixture ranges over *all* programs), but it shows the mechanics.
:::

:::solution
Suppose only two programs are in play. Program $A$ = "always output H" has some length $\ell_A$, so prior weight $w_A = 2^{-\ell_A}$. Program $B$ = "each toss is an independent fair coin" has length $\ell_B$, so prior weight $w_B = 2^{-\ell_B}$. Say $\ell_A = 4$ and $\ell_B = 6$, so $w_A = 2^{-4} = 1/16$ and $w_B = 2^{-6} = 1/64$.
**Likelihoods of the data** $x = \mathrm{H}^n$. Program $A$ produces $n$ heads with certainty: $P(x \mid A) = 1$. Program $B$ produces any specific length-$n$ string with probability $2^{-n}$: $P(x \mid B) = 2^{-n}$.
**Posterior weights** $\propto$ prior $\times$ likelihood. Unnormalized, $A$ has $w_A \cdot 1 = 1/16$ and $B$ has $w_B \cdot 2^{-n} = 2^{-n}/64$. As $n$ grows, $B$'s share shrinks like $2^{-n}$, so the posterior concentrates on $A$.
**Predict the next toss.** $P(\text{next}=\mathrm{H}) = P(A\mid x)\cdot 1 + P(B\mid x)\cdot \tfrac12$. For $n=3$: unnormalized $A = 1/16 = 0.0625$, $B = 2^{-3}/64 = 1/512 \approx 0.00195$; normalizing, $P(A\mid x) = 0.0625/(0.0625+0.00195) \approx 0.970$. So $P(\text{next}=\mathrm{H}) \approx 0.970\cdot 1 + 0.030\cdot 0.5 \approx 0.985$.
**Sanity check.** The prediction sits strictly between $1/2$ (what $B$ alone says) and $1$ (what $A$ alone says), and it climbs toward $1$ as $n$ increases — Occam's razor emerging automatically, since the shorter, better-fitting program $A$ dominates. Crucially, if a tail ever appears, $P(x \mid A) = 0$ and $A$ is eliminated outright, so the mixture never becomes overconfident in a falsifiable hypothesis.
:::

## Incompressibility, Martin-Löf Randomness, and Chaitin's Omega

<!-- section: incompressibility-chaitin -->

:::definition[c-incompressible string]{#c-incompressible}
A finite string $x$ is $c$-incompressible if

$$K(x) \ge |x| - c;$$

such strings are the finite analogue of "random".
:::

For an *infinite* sequence, Martin-Löf randomness is the correct notion: it requires $K(x_1\dots x_n) \ge n - c$ for all $n$, using prefix complexity $K$; the equivalence with passing all effective statistical tests is Schnorr's theorem.

Most strings are incompressible: the number of strings of length $n$ with $K(x) < n - c$ is less than $2^{n-c}$, so the compressible ones are exponentially rare.

:::definition[Chaitin's Omega]{#chaitin-omega}
$$\Omega = \sum_{p \text{ halts}} 2^{-|p|}$$

is the halting probability of the universal prefix-free machine — the probability that a randomly generated program halts, hence a real number in $(0,1)$.
:::

It is a random real: its binary digits are algorithmically random, it is uncomputable, and its bits encode the answers to all halting problems.

AIT implies that certifying incompressibility has a hard ceiling.

:::theorem[Chaitin's incompleteness theorem]{#chaitin-incompleteness}
For any consistent formal system able to reason about programs there is a constant $c$, roughly the system's own description length, such that the system cannot prove the true statement $K(x) > c$ for any concrete $x$ — even though such $x$ are abundant.
:::

:::intuition
A random string has no pattern that a program shorter than itself can exploit; any description is basically as long as the string.

Ω is a single real number that 'knows' whether every possible program halts. You can *approach* it from below — running programs and adding $2^{-|p|}$ each time one halts gives ever-better under-estimates — but you can never pin down its exact digits, because that would tell you which programs never halt. Knowing the first $n$ bits of Ω would let you settle halting for all programs up to length $n$.
:::

:::example
Show that almost every string is incompressible, then plug in numbers.
:::

:::solution
**Count the descriptions.** Programs shorter than $n-c$ have lengths $0, 1, \ldots, n-c-1$, so there are at most $2^0 + 2^1 + \cdots + 2^{n-c-1} = 2^{n-c}-1$ of them. Each program outputs at most one string, so fewer than $2^{n-c}$ strings can have $K(x) < n-c$.
**Count the strings.** There are exactly $2^n$ binary strings of length $n$. The compressible ones number fewer than $2^{n-c}$, so the incompressible ones ($K(x) \ge n-c$) number more than $2^n - 2^{n-c}$.
**Turn it into a fraction.** The incompressible fraction exceeds $\dfrac{2^n - 2^{n-c}}{2^n} = 1 - 2^{-c}$.
**Sanity check with $c = 10$, $n = 1000$.** The incompressible fraction is at least $1 - 2^{-10} = 1 - 1/1024 \approx 0.99902$, i.e. over $99.9\%$ of all 1000-bit strings cannot be compressed even by 10 bits. Note the bound $1 - 2^{-c}$ does not depend on $n$ at all: no matter how long the strings, only a $2^{-c}$ sliver can be shortened by $c$ bits.
:::

## Common Mistakes

- **Confusing Kolmogorov complexity K(x) with Shannon entropy H(X)**: K is for an individual string; H is an average over a distribution. For a string drawn from p, K(x) ≈ -log p(x) + O(1) with high probability (the asymptotic equipartition property in AIT).
- **Thinking K(x) is computable**: It is not; if it were we could solve the halting problem.
- **Believing that 'random-looking' strings are always incompressible**: Some strings that pass statistical tests can still have short descriptions (e.g., the binary digits of a computable irrational that looks random).
- **Forgetting the additive constant when comparing K across different machines or languages**: K_{U}(x) and K_{V}(x) differ by at most the size of a program that translates between U and V.
- **Assuming that because Ω is random its digits are 'patternless' in every sense**: While algorithmically random, the digits of Ω are highly structured (they encode halting information) and are not 'typical' under any computable measure in a strong sense.
- **Using AIT directly for practical compression**: K is uncomputable; practical compressors are approximations that work well on the kinds of redundancy humans and computers actually produce.

Kolmogorov complexity (also called algorithmic complexity or description complexity) provides an absolute, individual notion of the information content or "randomness" of a particular finite object — usually a string. It is the length of the shortest computer program that outputs exactly that object and halts.

Unlike Shannon entropy, which is an average over a probability distribution, Kolmogorov complexity is defined for each string by itself. It forms the foundation of algorithmic information theory.

## Definition

<!-- section: definition -->

Fix a universal programming language, or equivalently a universal Turing machine $U$. The Kolmogorov complexity of a string $s$ is

$$K(s) = \min \{\, |p| : U(p) = s \,\},$$

where the minimum is over all programs $p$ that cause $U$ to output $s$ and halt. If no such program exists — impossible for a universal $U$ — we set $K(s)=\infty$, but every finite $s$ has finite $K(s)$.

:::theorem[Invariance theorem]{#invariance-theorem}
The value $K(s)$ depends on the choice of $U$ only up to an additive constant independent of $s$.
:::

This is what makes $K$ a property of the string rather than of the programmer's taste in languages: two universal machines can disagree, but only by a fixed amount, so every asymptotic statement about $K$ survives the change.

:::intuition
K(s) is the size of the smallest "recipe" that a computer can follow to reproduce s exactly.

For the string consisting of the text of Hamlet, K(Hamlet) is much smaller than the number of bits needed to write the text literally, because a short program can contain the rules of English plus "print the play Hamlet".
:::

:::example
Estimate $K(s)$ for $s = $ the first $10\,000$ decimal digits of $\pi$, and see why it stays small.
:::

:::solution
**Write a generating program.** A spigot algorithm (or a Machin-like arctangent series) computes the digits of $\pi$ from scratch. Encode: the fixed digit-extraction routine (a constant number of bits, call it $c_\pi$) plus the target count $N = 10\,000$.
**Cost of the count.** Writing $N$ takes about $\log_2 10\,000 \approx 13.3$, i.e. $14$ bits.
**Total.** $K(s) \le c_\pi + 14 + O(1)$ — a few hundred bytes at most, dominated by the fixed routine, *not* by the $10\,000$ digits themselves.
**Sanity check by comparison.** Writing the digits literally would take about $10\,000 \times \log_2 10 \approx 33\,219$ bits. The program is smaller by a factor of hundreds, and — crucially — asking for the first *million* digits changes only the count from $14$ to $\approx 20$ bits, while the literal cost balloons to $\approx 3.3$ million bits. So $K(\pi\text{-digits})$ grows like $\log N$, confirming $\pi$ is highly compressible despite its digits passing every simple statistical test for randomness.
:::

## Relation to Shannon Entropy

<!-- section: relation-to-entropy -->

:::theorem[Algorithmic complexity matches self-information]{#k-vs-entropy}
If a string $s$ is generated by a computable probability distribution $P$, then with high probability under $P$,

$$K(s) = -\log_2 P(s) + O(1),$$

where the $O(1)$ depends on $P$ — the size of a program that knows $P$ — but not on the particular realization $s$. Moreover the expected complexity recovers the Shannon entropy,

$$\mathbb{E}[K(X)] \approx H(X),$$

again up to an additive constant.
:::

:::intuition
For data coming from a known probabilistic source, the algorithmic complexity of a typical realization is essentially the same as its self-information under that source.

On average, "how hard is it to describe a random draw" equals the entropy of the draw.
:::

:::example
For a long sequence of $n$ i.i.d. fair coin flips, each specific outcome $s$ has $P(s) = 2^{-n}$, so $-\log_2 P(s) = n$ for every $s$.
:::

:::solution
1. With overwhelmingly high probability $K(s) = n + O(\log n)$: you need roughly $n$ bits to describe the literal string plus a few bits to say "this is a raw bit string of length $n$". This matches $-\log_2 P(s) = n$, as the theorem $K(s) = -\log_2 P(s) + O(1)$ predicts.
2. The exception proves the rule. A string that happens to be $010101\ldots$ repeated has $K(s) \approx \log_2 n + O(1)$ (program: "print 01 repeated $n/2$ times") — far below $n$. This does *not* contradict step 2, because the theorem only holds "with high probability": the periodic string is one of the exponentially rare atypical outcomes. Its own self-information is still $-\log_2 P(s) = n$; the periodic string simply happens to be much more compressible than its probability suggests, which is exactly why such strings have vanishing probability.
3. **Sanity check.** Averaging over all $s$, $E[K(X)] \approx \sum_s 2^{-n}\cdot(\text{its }K) \approx n = H(X)$ for the uniform distribution on $n$ bits, recovering the entropy. The rare low-$K$ strings pull the average down only negligibly because they are so few.
:::

## Incompressible Strings and Algorithmic Randomness

<!-- section: incompressibility -->

:::proposition[Counting bound on compressible strings]{#counting-compressible}
There are at most $2^k - 1$ strings with $K(s) < k$. Consequently the vast majority of strings of length $n$ satisfy

$$K(s) \ge n - O(1);$$

they are incompressible.
:::

:::proof
There are $2^0 + 2^1 + \dots + 2^{k-1} = 2^k - 1$ programs of length less than $k$, and each program outputs at most one string.
:::

:::definition[Algorithmically random string]{#algorithmically-random}
Incompressible strings are called algorithmically random, in the sense of Martin-Löf or Chaitin. They pass every effective statistical test for randomness.
:::

:::intuition
There are only a few short programs, so only a few strings can be produced by short programs.

Most long strings have no hidden pattern or rule that would let you write a much shorter program to generate them; they are "random" in the deepest sense.
:::

:::example
Of the $2^{1000}$ binary strings of length 1000, fewer than $2^{990}$ have $K(s) < 990$.
:::

:::solution
1. Hence more than $99.9\%$ of all 1000-bit strings are incompressible by 10 or more bits.
2. Any particular string you pick at random will almost surely be one of them.
:::

## Uncomputability and Incompleteness

<!-- section: uncomputability -->

:::theorem[Uncomputability of K]{#k-uncomputable}
$K(s)$ is uncomputable: there is no algorithm that on input $s$ always halts and outputs the exact value $K(s)$.
:::

The limitation is not merely algorithmic. By Chaitin's incompleteness theorem, in any consistent axiomatic system powerful enough to reason about programs there is a fixed constant $c$, depending on the system, such that the system cannot prove $K(s) > c$ for any concrete string $s$.

:::intuition
You cannot write a program that looks at an arbitrary file and tells you the size of the smallest program that produces that file (it would solve the halting problem).

Formal mathematics has limits: it cannot certify that a particular long string is "truly random" (has high K) beyond a certain point that depends on the axioms.
:::

:::example
Suppose your favorite theorem prover could, for every $n$, output a string $s_n$ of length $n$ together with a proof that $K(s_n) > n - 100$.
:::

:::solution
1. Then you could use that to solve halting for programs up to size $n-100$, contradicting the undecidability of the halting problem.
2. Hence no such prover exists.
:::

## Common Mistakes

- **Confusing Kolmogorov complexity with gzip or any practical compressor size**: Practical compressors give upper bounds on K; K is the ultimate (uncomputable) lower bound.
- **Thinking every string has low K because 'you can always write a program that prints it literally'**: The literal program costs roughly |s| bits plus overhead; for random s this is essentially optimal.
- **Believing K is computable in practice for interesting strings**: While we can compute upper bounds (by finding short programs) and sometimes good lower bounds via compression or proofs, the exact value is uncomputable.
- **Forgetting the additive constant in the invariance theorem**: Different universal machines differ by at most a constant; statements about K(s) → ∞ or K(s) < |s| - 100 are robust, but exact numbers are machine-dependent.
- **Identifying 'random-looking' with low Kolmogorov complexity**: Visually random strings can still be generated by short programs (e.g., the digits of π or the output of a good PRNG with a short seed). True incompressibility is much stronger.
- **Applying K directly to infinite objects without care**: For infinite sequences one studies the limsup of K(prefix_n)/n or prefix-free variants; the plain K above is for finite strings.

This advanced treatment of Kolmogorov complexity (K-complexity) focuses on its mathematical properties, fundamental limitations, and deep connections to induction, learning, and the foundations of mathematics. While a basic introduction appears earlier, here we examine why K is uncomputable, what that implies for science and AI, and how it formalizes Occam's razor and randomness for individual objects.

## Properties of Kolmogorov Complexity

<!-- section: kc-properties -->

:::proposition[Chain rule for Kolmogorov complexity]{#k-chain-rule}
Up to additive constants,

$$K(x,y) = K(x) + K(y \mid x^*) + O(1),$$

where $x^*$ is a shortest program for $x$.
:::

This is the algorithmic analogue of $H(X,Y) = H(X) + H(Y|X)$ — the same bookkeeping, with programs in place of distributions.

:::proposition[Subadditivity and invariance under computation]{#k-subadditive}
$K$ is 'almost' subadditive,

$$K(x,y) \le K(x) + K(y) + O(1),$$

and invariant under computable transformations: for any computable $f$,

$$K(f(x)) \le K(x) + c_f.$$
:::

Plain Kolmogorov complexity (not prefix-free) and prefix complexity differ by at most a logarithmic term; most theorems hold for both.

:::intuition
The shortest description of the pair (x,y) is basically 'shortest description of x' plus 'shortest description of y given that you already have the shortest description of x'.

Any computable processing of x cannot increase its complexity by more than the size of the processing program.
:::

:::example
Apply the properties to two contrasting strings and check the chain rule.
:::

:::solution
**Invariance under computable maps.** Let $s$ = the first $n$ digits of $\pi$. Because a fixed program computes $\pi$'s digits from $n$ alone, $K(s) \le K(n) + c_\pi$, where $c_\pi$ is the size of that program. With $K(n) \le \log_2 n + O(1)$ this gives $K(s) \le \log_2 n + O(1)$ — small, confirming $\pi$'s digits are highly structured.
**Incompressible contrast.** A typical random string $r$ of length $n$ has $K(r) = n + O(1)$; no computable transformation shrinks it, because $K(f(r)) \le K(r)+c_f$ bounds growth but there is nothing to gain when $r$ is already incompressible.
**Chain rule on independent halves.** Take $x$ and $y$ to be two *independent* random strings, each of length $n$, so $K(x) \approx n$ and $K(y) \approx n$. Since $y$ shares no structure with $x$, knowing $x^*$ gives no help: $K(y \mid x^*) \approx K(y) \approx n$. The chain rule then gives $K(x,y) = K(x) + K(y\mid x^*) + O(1) \approx 2n$.
**Sanity check against subadditivity.** Subadditivity says $K(x,y) \le K(x)+K(y)+O(1) \approx 2n$, consistent with step 3. Now contrast the *dependent* case $y = x$: then $K(x,x) = K(x) + K(x \mid x^*) + O(1) \approx n + O(1)$, far below $2n$, because once you have $x^*$, reproducing the second copy is free. The chain rule correctly charges nothing for redundant information — the algorithmic mirror of $H(X,X)=H(X)$.
:::

## Uncomputability and Incompressibility

<!-- section: uncomputability-incompressibility -->

$K(x)$ is upper semi-computable — we can approximate it from above by dovetailing all programs — but it is not computable.

:::proof
If $K$ were computable we could solve the halting problem: run the candidate program for $|p|$ steps; if it has not halted, its output (if any) would have $K$ at most $|p| + O(1)$, contradicting a large enough lower bound.
:::

Recall that a string $x$ is $c$-incompressible when $K(x) \ge |x| - c$. By the counting argument, for any $c$ the fraction of $n$-bit strings that are $c$-incompressible tends to $1$ as $n \to \infty$.

:::theorem[Incompressibility is Martin-Löf randomness]{#ml-randomness}
Martin-Löf randomness — passing all effective statistical tests — is equivalent, up to constants, to being incompressible.
:::

:::intuition
There is no algorithm that, given any x, prints the number K(x). If there were, you could detect non-halting programs by checking whether their 'would-be' output has too low a complexity.

Most strings are incompressible; only a tiny fraction have short descriptions. 'Randomness' for a single string means 'no short program describes it'.
:::

:::example
Prove $K$ is uncomputable via the "Berry paradox" construction (the cleanest self-contained argument).
:::

:::solution
**Assume for contradiction** that $K$ is computable — there is an always-halting algorithm $\text{Kcomp}(x)$ returning $K(x)$.
**Build a short paradoxical program** $Q$. Given a target number $m$ (hard-coded into $Q$), $Q$ enumerates strings $x = 0, 1, 00, 01, \ldots$ in order, calls $\text{Kcomp}(x)$ on each, and outputs the *first* string $x_0$ it finds with $K(x_0) \ge m$. Such an $x_0$ always exists because, by the counting argument, most strings have complexity near their length, so complexities are unbounded.
**Measure $Q$'s length.** $Q$ consists of a fixed enumerator plus $\text{Kcomp}$ (a constant $d$ bits) together with the number $m$ (about $\log_2 m$ bits). So $|Q| \le \log_2 m + d$. Since $Q$ outputs $x_0$, we have $K(x_0) \le |Q| \le \log_2 m + d$.
**Derive the contradiction.** By construction $K(x_0) \ge m$. Combining, $m \le K(x_0) \le \log_2 m + d$. But $m > \log_2 m + d$ for all sufficiently large $m$ (the left side grows linearly, the right only logarithmically), so choosing such an $m$ makes $m \le \log_2 m + d$ false.
**Sanity check.** The contradiction came *only* from assuming $\text{Kcomp}$ exists and always halts. Everything else (the enumerator, hard-coding $m$) is plainly implementable. Hence no such $\text{Kcomp}$ exists: $K$ is uncomputable. Note $K$ remains upper semi-computable — dovetailing all programs gives ever-better upper bounds on $K(x)$ — it is only the exact value that is out of reach.
:::

## Applications: Induction, Learning, and Incompleteness

<!-- section: applications-incompleteness -->

Solomonoff induction (universal prior m(x) based on K) is a formal, parameter-free embodiment of Occam's razor for sequence prediction. Its predictions converge to the truth for any computable data-generating process.

:::definition[Minimum description length]{#mdl}
In machine learning, the minimum description length (MDL) and minimum message length (MML) principles select the model minimizing

$$K(\text{model}) + K(\text{data} \mid \text{model}).$$
:::

They are practical approximations to $K$, and the two terms are exactly the fit-versus-complexity trade-off, priced in the same units.

Chaitin's incompleteness: any consistent formal system of 'complexity' c can prove statements of the form 'K(x) > n' only for n bounded by c + O(1). Thus mathematics cannot prove that particular long strings are random.

Levin's universal search (Kt complexity with time-bounded K) gives an optimal (up to constants) algorithm for inverting any computable function or solving any NP search problem, given enough time.

:::intuition
When choosing among models that fit your data, prefer the one whose description (the model itself plus the data encoded using the model) is shortest. That is formal Occam.

A fixed axiom system cannot certify the randomness of strings much longer than the axioms themselves; there will always be 'random' mathematical facts that the system cannot prove.
:::

:::example
Use MDL to choose between a simple and a complex model, with numbers.
:::

:::solution
**Set up the two candidates.** We have data $D$ and two models. Model $M_1$ is a low-degree fit: cheap to describe, $K(M_1) = 30$ bits, but it leaves larger residuals that cost $K(D \mid M_1) = 100$ bits to encode. Model $M_2$ is a high-degree fit: expensive to describe, $K(M_2) = 200$ bits, but it hugs the data so the residuals cost only $K(D \mid M_2) = 10$ bits.
**Compute total description lengths.** $L_1 = K(M_1) + K(D \mid M_1) = 30 + 100 = 130$ bits. $L_2 = K(M_2) + K(D \mid M_2) = 200 + 10 = 210$ bits.
**Pick the minimum.** $L_1 = 130 < 210 = L_2$, so MDL selects the *simpler* model $M_1$ even though $M_2$ fits the data better.
**Sanity check — the overfitting guard.** $M_2$ reduced residual cost by $100 - 10 = 90$ bits but paid $200 - 30 = 170$ extra bits to describe its added parameters. Since it spent more than it saved, its extra complexity was not "paid for" by the data — the hallmark of overfitting. MDL's single number, total code length, captures exactly this trade-off with no separate regularization knob.
:::

## Common Mistakes

- **Treating K(x) as a practical compression metric for arbitrary files**: While theoretically ideal, K is uncomputable; real compressors (gzip, etc.) are computable approximations tuned to specific redundancies.
- **Forgetting the O(1) additive constants when making asymptotic claims**: Many equalities in AIT hold only up to constants; statements like 'K(x) = H(x) for typical x' are true with high probability but the deviation can be logarithmic or worse in some regimes.
- **Believing that a string with high K must 'look random' to every statistical test**: There exist strings that are incompressible yet fail some non-effective tests; the equivalence is with Martin-Löf tests (effective ones).
- **Confusing prefix-free K with plain (monotone) complexity**: The technical differences matter for the chain rule and for Ω; most high-level conclusions are the same.
- **Assuming that because a string is generated by a short program it cannot be used as a cryptographic key**: If the program is secret and the output is long, the output can still have high 'computational' entropy even if K is small.
- **Using AIT to 'prove' that science is impossible or that induction fails**: On the contrary, Solomonoff induction succeeds for all computable realities; the uncomputability is a limit on perfect prediction, not a refutation of the method.
